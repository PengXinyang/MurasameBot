# MurasameBot

丛雨的跨平台社交内核，首个实际适配目标为 B 站。当前版本 `0.1.0`，采用 **Python 3.12+**。

Python 更适合当前单人迭代：角色配置、模型接口、内容处理与既有 B 站实现都容易接合；数据库和调度首期用标准库即可。Java 更适合已有 Java 团队或统一 JVM 部署的场景，本项目目前没有这些前提。模块之间使用端口接口，未来 QQ、微信适配器复用同一套内核。

## 当前实现

- 视频及动态评论区的 @ / 回复通知读取、首次基线和重复事件识别。
- 获取评论线程、生成中文角色回复、排队发送到对应楼层。
- B 站互关用户的文字私信收发；单向关注、仅粉丝、陌生人、系统消息和撤回消息不回复，主人也需互关。
- 私信日常聊天、同会话上下文和主人视频委托自然衔接；模型审核通过自动发送，未通过或审核异常交由人工。
- 监测主人新视频和新动态，生成主动评论。
- 独立转发主人新视频对应的投稿动态与新动态，评论和转发分别开关、分别去重。
- 按时刻搜索 Pixiv/X 的游戏角色插画，筛选后生成丛雨配文；仅对配置授权范围内的作品发布图片，附画师和原作链接。
- 统一对外代理，默认 `http://127.0.0.1:7890`，可切换 SOCKS5；管理台仍使用 8766。
- 按星期、时区、时间窗口和分区发现视频，根据标题、简介及可取得的字幕决定旁观、评论、接话或推荐。
- 自主浏览时可给视频留评论，并独立回复一条实际读到的其他用户评论；两个开关及去重分别控制。
- 回复生成时根据语气选择 0～2 个表情，评论优先使用账号可用的丛雨原生表情；私信使用 Unicode 表情，完整正文与表情一起审核。
- 动态及图文评论区被提及时读取原正文和图片，依据成功的视觉分析生成回复。
- 对感兴趣的视频点赞、投 1 枚硬币，对感兴趣的动态/图文点赞；开关和去重彼此独立。
- 使用实际 UID 到昵称映射编码 @ 主人，记录回执和提及是否确认。
- 统一人物绑定、范围隔离的偏好记忆、可取消/修改的持久找视频委托。
- SQLite 持久化、发送额度、并发领取控制、重启恢复、结果未知时不重发。
- 丛雨文字人设导入、本地管理台、命令行和无网络模拟演示。

**这些是代码实现范围，不代表真实账号端到端验收已经通过。** 已用本地配置验证真实模型的合成聊天生成与审核，以及 B 站登录、互关查询和私信读取；开发期间未向 B 站发送真实评论或私信。QQ、微信的真实适配器尚未实现；跨平台需求可通过本地统一事件输入验证。

## 启动

在本目录执行，不必激活虚拟环境：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev,login]"
.\.venv\Scripts\python.exe run.py doctor
.\.venv\Scripts\python.exe run.py demo
```

本次开发环境已在 `.venv` 安装本地命令入口及依赖。`demo` 使用固定场景模型和假平台，不联网、不计费、不改变正式账号数据库；它展示“模拟微信需求 → 保存任务 → 查找视频 → 模拟 B 站提及 → 重启去重”。

## 填写模型和账号

把 `.env.example` 复制成 `.env`，在本机填写：

```dotenv
MURASAME_MODEL_BASE_URL=https://your-service.example/v1
MURASAME_MODEL_NAME=your-model-name
MURASAME_MODEL_API_KEY=your-private-key
MURASAME_OWNER_UID=your-bilibili-uid
```

模型输出默认不传 `max_tokens`，使用模型服务的官方默认额度；可在 `model.max_output_tokens` 配置正整数覆盖。模型生成额度与 B 站正文长度分别配置。

服务需支持 `/chat/completions`、`response_format: {"type":"json_object"}` 和结构化 JSON 文本输出。地址填写到 `/v1` 等基础路径，程序追加 `/chat/completions`。本地无密钥服务可以留空密钥。修改 `.env` 后重启工作进程。

主人 UID 从本地 `.env` 的 `MURASAME_OWNER_UID` 读取，也可在被 Git 忽略的 `config.local.yml` 中覆盖 `bindings`。公开示例不含个人 UID；没有填写就不建立主人绑定。请使用你准备作为 AI 的账号扫码：

```powershell
.\.venv\Scripts\python.exe run.py login
```

用 B 站 App 扫描生成的 `.secrets/login-qr.png` 并确认。凭证写入 `.secrets/bilibili.json`，不会输出 Cookie。`bilibili.robot_uid` 可填预期机器人 UID，用来防止误登账号。头像由你在平台手动设置。

随后进行只读登录检查：

```powershell
.\.venv\Scripts\python.exe run.py doctor --online
```

Cookie 失效时程序暂停相应出站；重新扫码并 `resume`。首版没有自动 Cookie 刷新，也不会处理验证码或切换其他账号继续操作。

网络默认走本机 7890 代理；代理服务尚未启动时，在 `config.local.yml` 设置 `network: {proxy_enabled: false}`。代理协议、美图时刻、授权名单与转发开关的字段见 `config.yml`；本机补充说明位于仓库上一级的 `docs/新增功能配置.md`，不随仓库分发。

## 管理台与工作循环

```powershell
# 仅管理台：不会启动平台轮询、模型调用或发布
.\.venv\Scripts\python.exe run.py serve

# 填好模型、登录后，启动管理台与工作循环
.\.venv\Scripts\python.exe run.py serve --with-worker

# 也可以仅运行后台工作循环
.\.venv\Scripts\python.exe run.py run
```

打开终端打印的本机管理链接。界面采用薄荷绿与米白配色，首页显示丛雨立绘、消息队列与运行计划。设置分为“浏览与互动”“消息与模型”“表情与分享”，保留全部额度和功能控件；手机端使用响应式布局。图片来自 character/avatar 的固定白名单，缺失时不影响管理接口；不会作为账号头像或消息附件发送。该链接含管理令牌，只留在本机；服务只绑定 `127.0.0.1`。面板可设置浏览时段、星期、分区、兴趣、每轮数量、发布模式，查看草稿、记忆、委托和活动记录，并暂停或恢复任务。配置改动下一轮生效。

默认 `mode: reviewed`、`review.strategy: inline`：模型在一次生成中同时返回正文、表情和 `can_send`（布尔值）、`review_reason`（简短中文原因）。通过即进入发送队列；不通过、判断缺失或格式无效、实际正文/表情与判断不一致时，转入“发布与草稿”，不再追加模型复核。管理台可切换 `review.strategy: independent`，保留生成后独立模型复核。人工批准不会绕过互关、暂停、来源和有效期检查。`mode: draft` 表示全部人工审核，`mode: auto` 表示跳过模型审核直接按程序策略发送。切回全部人工模式会把尚未执行的自动动作转回待审核，已开始的网络请求可能无法撤回。

评论/@ 和私信默认每 15 秒检查（`bilibili.reply_poll_seconds`），主人作品默认每 90 秒检查（`bilibili.poll_seconds`）。持续运行时，收件、消息生成/审核、后台浏览和平台发布分别调度，模型慢请求不会阻塞下一轮收件。平台收件本身的网络耗时仍可能延后检查，当前没有接入平台推送。

`processing.model_concurrency` 默认 4，可在管理台设置 1～32。多个独立会话可同时调用同一个 key；生成、审核和视觉共用此请求并发上限，同一会话及已绑定同一人的私聊保持处理顺序。每个任务持有自己的 HTTP 客户端，平台实际发布仍串行领取并遵守发送间隔。并发改变不会增加每日额度，已发出的模型请求不会被中止。

管理台“消息并发与收件”“额度、间隔与回复长度”可修改并发、分页、每日模型调用、每日发送总量、推荐上限、发送/推荐间隔、动作/委托有效期、重试次数及回复长度。顶部显示队列数量与当前收件警告。默认生成时判断不追加审核调用，普通文字回复通常只需一次生成请求；主人需求提取、视觉分析、记忆维护仍可能有各自调用。选择独立复核时，生成与复核分别计次。

私信默认开启（`bilibili.private_messages_enabled: true`），仅接收已验证互关用户的新文字消息。首次启用只建立历史水位；重启沿用水位，不重回旧私信。生成前、发送前都会核验关系，查询失败时拒绝发送。支持同会话近期上下文；已绑定主人还可通过私信保存兴趣或找视频委托，其他互关用户不会被当作主人。

## 浏览与推荐

`config.yml` 中配置：

```yaml
browsing:
  enabled: true
  weekdays: [0, 1, 2, 3, 4, 5, 6]
  windows:
    - start: "19:00"
      end: "21:00"
  categories: ["4", "188"]
  interval_minutes: 60
  videos_per_round: 2
  candidate_limit: 6
  interests: [游戏开发, 人工智能]
  owner_interests: []
```

面板设置写入 `config.local.yml`，优先于 `config.yml`。`categories` 显示适配器的分区参考表；这些是社区接口兼容 ID，需要核对实际返回内容，不能视为网站当前导航的官方完整目录。

`browsing.comment_videos`、`browsing.reply_comments`、`browsing.recommend_owner` 分别控制主动视频评论、主动评论区接话和向主人推荐，默认允许。模型可在一轮中生成一条视频评论/推荐及一条评论区接话，也可全部旁观；每条动作分别占用发送额度并经过审核。只回复实际取得的评论，排除自己的评论并保留真实 root/parent。额外社交接话不能完成主人的找视频委托。被动 @ / 回复通知不受这三个主动开关影响。

`expressions.enabled` 控制语气表情，`max_per_message` 可选 1 或 2，允许模型选择不用；`preferred_keywords` 默认 `[千恋万花, 丛雨]`，按顺序优先匹配官方千恋万花表情包，再优先丛雨相关表情。表情选择与正文在同一次模型生成中完成，无需额外调用。评论表情来自登录账号的实际面板，过滤不可访问或已到期项，发送前再次检查。`kaomoji_enabled` 默认开启，允许搭配最多 1 个文字颜文字（如 `(*´▽｀*)`、`(≧▽≦)`），与原生表情合计仍不超过 `max_per_message`。模型根据语境决定不用、只用一种或两种搭配；颜文字计入字数并随完整正文审核。私信可使用颜文字或 Unicode，不假定评论表情可在私信渲染。管理台可设置开关、数量、优先关键词和缓存，并只读刷新账号可用表情；已核验当前账号含 `[千恋万花表情包_丛雨Ciallo]`。

未知表情标识、重复及超出上限的选择不会插入正文；表情计入字数预算，预算不足时省略表情。模型审核检查实际完整文字与表情是否符合语境。账号权限在发送前发生变化时不使用失效表情。原始角色图片仍不发送，也不自动购买表情包。

分区留空时不做一般探索，但有效的明确找视频委托仍可搜索。关闭浏览总开关时，委托和一般浏览都不主动读取新候选；通知回复、主人新内容监测独立运行。每轮到期委托优先于一般探索。跨午夜窗口归属开始的星期。

视频默认分析“标题＋简介＋可取得的字幕”（`bilibili.read_video_subtitles: true`）。没有字幕或普通字幕接口不可用时，按标题与简介继续分析（`browsing.allow_metadata_video: true`）。不下载视频，也不要求完整观看。字幕最多读取前 3 个分 P，受文本预算限制；不会用字幕替换或丢弃简介。评论和推荐不得编造未读画面或声称完整观看。可关闭字幕读取，仅用标题与简介。尚未接入 ASR 或视频帧分析。

动态图片通过通用 `VisionService` 分析，支持动态正文提及及评论区提及。适配器提取动态正文、原动态引用与图片，视觉服务下载并校验真实图片，再将成功的逐图描述用于回复和文字审核。默认最多前 9 张、每张 8 MiB、每次合计 24 MiB；覆盖范围及失败记录保存在视觉证据中。读取失败时只依据可取得的文字，不猜图片内容。GIF 不保证理解完整动作。

`vision.enabled` 控制图片理解。默认复用主模型，模型必须支持图片输入；如需独立视觉服务，在 `.env` 设置 `MURASAME_VISION_BASE_URL`、`MURASAME_VISION_MODEL_NAME`、`MURASAME_VISION_API_KEY`。切换到另一服务地址时不会自动转发主服务密钥。下载图片使用独立无 Cookie 客户端和允许的 B 站图片域名，仍走全局代理。

兴趣互动开关：

```yaml
engagement:
  video_like: true
  video_coin: true
  dynamic_like: true
```

兴趣由模型独立判断，不评论也可互动；满足主人搜索需求不自动等于丛雨自己感兴趣。投币固定 `multiply=1`，发送前查询该视频已有投币及当前余额，已经投过、余额不足 1 枚或余额无法确认时不投币。不会给动态投币。点赞使用明确的“点赞”状态，不使用切换或取消赞。三类互动与文字评论分别去重；结果未知不自动重试。

互动与其他动作共用每日发送总额度（当前字段 `limits.daily_comments` 默认 20）和发送间隔。`reviewed` 下文字按所选策略判断能否发送，点赞和投币由兴趣判断加程序检查执行；`draft` 下互动也需人工批准。自主浏览产生的互动遵守浏览窗口，通知触发的互动独立运行。控制台可以单独开关，关闭后排队互动也会在发送前失效。

首轮通知和主人内容列表只建立基线，不评论历史积压。默认每类通知最多 3 页、每页 30 条；评论/@ 去重合并后最多接收最新 90 条，私信入口同样最多接收最新 90 条（`bilibili.inbox_batch_limit`）。超过分页或数量上限时保留选中的消息并显示管理台警告，不再因分页超限让整批失败。较旧超限消息不保证补回，私信截断会推进所读范围的水位。网络、登录和风控错误仍按原策略处理。平台接口并非正式开放授权保证，兼容性须用自己的可用账号逐项验收。

## 记忆、委托与后续 QQ / 微信

`character/settings.yml` 保留原样，`character/text_profile.yml` 保存从来源提炼的社交文字角色资料。公开资料和主人称谓分开使用，原始人设中的私人姓名、关系和秘密不整段发送到公开模型上下文。人设版本更新不会清空数据库。

所有文字只用中文；日语仅为将来 QQ / 微信语音生成预留，本版没有翻译或 TTS。对外人设图片发送和自动头像未接入；本地管理台使用原始丛雨 PNG 作装饰。

绑定自己的后续平台身份后，可导入统一事件测试意图识别：

```powershell
.\.venv\Scripts\python.exe run.py bind wechat your-verified-user-id
.\.venv\Scripts\python.exe run.py ingest examples/owner_request.json --process
```

将示例中的 `actor_id` 改为你已核验绑定的标识，时间改为当前时间。`--process` 会调用真实已配置模型，可能计费，但此命令不发送消息。真实微信/QQ消息读取需要后续实现对应适配器；昵称相同不建立身份关系。

明确请求成为一次性任务；兴趣不会自动变成周期任务。明确更正或取消会使旧任务和待发动作失效，删除来源记忆会阻止旧事件重放恢复该需求。明确要求“每天/每周/持续推荐”才建立周期任务。公开推荐不携带源私聊原文；敏感主题会停止公开投递，供本地处理。

## 长期记忆与每日回顾

记忆采用“原文归档＋近期对话＋带来源的分段摘要/事实＋按需检索”。原文不会因条数增加而被覆盖；数据库保存已处理的真实对话及平台确认受理的回复，草稿、失败和结果未知的发送不算已说过的话。旧版已处理记录由后台分批回填，不重放消息或发送动作；首轮历史基线和未拉取到的超限消息不计入完整记忆。

回复时先按 agent、人物、会话、公开/私聊及用途过滤，再组合近期消息、相关原文、摘要与偏好。支持 FTS5 trigram 和中文短词兜底检索；SQLite 缺少该扩展时仍可按范围查文字。只有明确授权用途的主人视频偏好能供跨平台推荐使用，普通私聊原文与日记不会进入公开评论。QQ/微信仍需各自的真实连接器。

默认配置在 `memory` 下，均可在管理台“记忆”页调整：

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| enabled | true | 开启检索与维护；关闭保留数据 |
| recent_messages | 20 | 近期用户与助手消息合计数 |
| recall_limit | 8 | 相关原文召回上限 |
| context_characters | 12000 | 回复记忆输入的字符预算 |
| summary_messages / batch_messages | 40 / 80 | 未总结旧消息触发数 / 单批上限 |
| input_characters / pressure_ratio | 24000 / 0.75 | 总结输入预算 / 压力触发比例 |
| review_time | 23:00 | 按项目时区回顾到该时刻的新记录 |
| daily_call_limit | 10 | 维护每日调用硬上限，0 表示不调用模型 |
| retry_minutes | 10 | 失败后的最短重试间隔 |

达到消息阈值或预算压力时做增量总结；少量长消息也可提前压缩。正常情况下保留近期窗口，压力触发时至少保留最近两条原文。到回顾时刻整理尚未回顾的记录；离线积压会在恢复后按范围分批补齐，没有新内容不调用模型。回顾只保存本地日记与相处记录，不发布动态，不覆盖 `character/settings.yml`。字符预算是输入估计，不是模型 token 计费，也不修改 `max_output_tokens: null` 的服务默认输出策略。

维护由现有工作协调器的单独一条后台通道执行，优先让出新消息和审核，共享模型总并发与 `model.daily_call_limit`。失败、额度耗尽或来源发生变化时保留原文，不能把部分失败当作成功覆盖历史。

管理台提供原文查询/当前结果 JSONL 导出、来源查看、置顶、更正、遗忘、指定范围摘要重建、维护失败重试，以及上下文已选来源和预算省略数量。事实是模型基于用户原文提取的解释，保留原文依据供核对；人工更正保留版本，自动事实修订只允许引用同范围已有事实。

删除来源会同步使相关摘要、事实、日记、索引及待发回复失效，取消关联未完成委托；重启和回填遵守删除标记。为避免使用旧内容，记忆删除/更正或绑定撤销也可能取消其他基于旧记忆版本的待发回复，需要重新生成。已经发送到平台的内容无法通过本地遗忘撤回；主动下载的导出文件与离线备份属于独立快照，不自动跟随删除。

首次打开旧版数据库时会先生成相邻的 `数据库名.v1-backup`，再事务迁移至 v2。备份包括已提交 WAL 数据，不覆盖已有备份。恢复旧版本须停止工作循环后由操作者处理备份；程序不会自动把备份重新导入。数据库和备份均应保存在本地私密存储，Docker 请持久化配置的数据库目录。

参考 [dsh-world](https://github.com/chenkezhen480/dsh-world) 的归档、上下文压缩、每日回顾与自述版本设计，在现有 Python/SQLite 架构中独立实现，没有引入 DSH/Node 宿主、QQ 桥或 Windows 微信原生引擎。

```powershell
.\.venv\Scripts\python.exe run.py reject ACTION_ID
```

超时或进程中断可能意味着评论已经发出。状态 `unknown` 不自动重试；先到平台核对，再记录实际结果：

```powershell
.\.venv\Scripts\python.exe run.py resolve ACTION_ID --state accepted --external-id ACTUAL_COMMENT_ID
# 或确认没有发出后，记录失败（仍不会自动重发）
.\.venv\Scripts\python.exe run.py resolve ACTION_ID --state failed
```

平台“受理”不证明公开可见。提及字段未得到确认时也保留待核对状态。所有发布统一经过队列，额度在事务内预留。
