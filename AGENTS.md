# MurasameBot implementation rules

## 仓库项目记忆与工作流程

这些文件是开发者/代理的项目记忆，不是运行时人设、用户聊天记忆或模型提示词。 当前功能与待办总览见 [STATUS.md](docs/STATUS.md)，开始新任务时先核对其快照与实际代码是否一致。

1. **开始每个新任务前**：先读本文件，再读 [架构](docs/ARCHITECTURE.md)、[决策](docs/DECISIONS.md)、[开发日志](docs/DEVELOPMENT_LOG.md)；按 [文档索引](docs/README.md) 阅读相关专题，再检查实际代码、Git差异和本次用户指令。用户当前明确要求优先，旧日志和规划不能代替代码事实。
2. **完成重要开发任务后**：更新 `docs/DEVELOPMENT_LOG.md`，写明日期、范围、实现、验证方法/结果、未验证部分、已知问题及下一步。明确区分“已编码”“模拟测试通过”“真实只读验证”“用户确认实际效果”；不把模型判断或平台受理当作送达/公开可见。
3. **架构或关键行为决策变化时**：更新 `docs/DECISIONS.md`，记录原因、选项、未采用方案、影响及取代的旧决策；同时更新架构与相关操作说明。没有证据的历史原因标为未知，不补写推测。
4. **保持规范与实现缺口可见**：下文是持续遵守的约束，并不证明所有旧路径都已满足。先看开发日志中的问题与修复状态；以具体代码和反例回归确认闭环，不得把测试总数当作所有问题已解决的依据。摘要重建与普通主动推荐的两项旧缺口已在2026-10-29专项修复，维护饥饿和备份等待办仍需保留。
5. `docs/` 现在纳入仓库。旧的“全部补充文档只留上一级”约定由2026-10-29的用户要求取代。按 [来源整理记录](docs/PROVENANCE.md) 提炼旧资料，不批量导入本机配置/日志/抓包/诊断脚本或过期结论。
6. 只记录代码或已有对话可确认的信息。公开文档不得包含真实主人UID、私人姓名/关系原文、Cookie、密钥、管理token、二维码会话、私信正文、个人观看清单或原始网络请求。用配置项和占位符说明。
7. 仅整理文档时不改业务代码；已有业务差异保留原样。推送时显式审查文件范围，已有业务任务与文档任务分开提交，说明验证边界。不得把未完成的QQ/微信/X、Docker或视频投稿写成已实现。
8. **每次完成一个工作后自动提交并推送远端（用户2026-10-30明确要求）**：完成相应验证、更新开发记录并审查本次差异后，自行提交并推送到当前分支的已配置远端，无需再次询问是否推送。使用明确的文件清单暂存，只提交本次工作或用户明确要求一起发布的已完成改动；不得提交本地凭证、私密配置、数据库、聊天/观看记录、二维码、原始抓包或测试运行产物。保留他人/并发未完成改动，不强推、不覆盖远端历史。若远端有新提交、权限/认证或网络导致推送失败，先采用不丢失改动的方式处理；无法完成时明确说明本地提交与远端推送的实际状态，不将提交成功说成推送成功。用户本次已经授权将此前QQ私聊与QQ/B站联动代码一并发布。

## Product scope

Build a reusable social-agent core. Bilibili is the first live platform; later QQ and WeChat adapters must reuse the same identity, persona, memory, intent, scheduling, and action-policy services. Repository architecture, decisions and implementation status live in `docs/`. Earlier parent-workspace plans remain historical sources, not evidence of working integrations.

## Dependency direction

- Domain code must not import platform SDKs, platform adapters, HTTP clients, model-provider SDKs, or database implementations.
- Application services depend on domain models and port interfaces. Adapters implement ports. The composition root wires implementations together.
- Do not put Bilibili UID, BV/AV/oid/rpid rules, OneBot IDs, or WeChat message formats in shared business decisions. Use typed platform references at adapter boundaries.
- Different platform adapters must not call one another. Same-platform protocol helpers/mixins may compose one adapter. A WeChat request leading to a Bilibili recommendation goes through the shared intent and task services.
- Choose one conversational decision owner per agent. Platform plugins and scheduled jobs must not create parallel autonomous reply loops.
- Configuration and scheduling are platform-independent; platform-specific categories and API parameters are translated in adapters.

## Identity and memory

- Platform handles map to a verified canonical person. Nicknames or model claims do not establish identity.
- Conversation archives and memory products use the same agent/person/conversation/visibility/purpose filters before retrieval or summarization. Preserve original records and source relationships; summaries must not silently replace archives. Only accepted outgoing text counts as dialogue, not drafts, failures, or ambiguous writes.
- Incremental summaries, explicit-source facts, private daily journals and reflection versions are derived data. Never rewrite the fixed character source, infer permissions from a journal, or replace task execution state with a summary. Model-extracted facts need an exact quote from a user source; corrections and later explicit revisions take precedence.
- Derived-memory IDs include the checked memory epoch. Identical text in a new rebuild generation creates a new product while old inactive products stay inactive; never blindly reactivate a historical row on conflict. Capture the epoch before reading owner preferences, propagate it to all output from the decision (recommendations, comments, secondary replies and reactions), and recheck after generation, enqueue and before the write. Legacy proactive actions missing a memory revision require regeneration, including after manual approval.
- The user authorizes private observation-based diary thoughts (2026-10-29). Generate them in the existing memory-maintenance lane and budgets, after the configured daily review cutoff, with an independent owner-history diary switch. Treat watched metadata as past observations, never dialogue, confirmed preferences, shared experiences or tasks. Keep these journals in a dedicated private purpose and provenance table; do not inject them into normal chat/public prompts. Clearing/revoking/retention expiry scrubs affected journal text; forgetting a journal keeps coverage so the same observations do not recreate it. Recheck current configuration and sources after generation. Dashboard memory, diary, relationship reflection and owner history are independent pages.
- Forgetting and binding revocation invalidate source-linked products, indexes, context caches and affected queued replies. Recheck memory revision and active sources at summary commit and before dispatch; backfill must respect tombstones and never replay actions. Memory maintenance uses one bounded lane, the shared model limiter and both maintenance/global hard budgets.
- Scope all state by agent, person, conversation, visibility, and purpose as appropriate. Filter retrieval permissions before similarity search.
- Store provenance, time, confidence/status, and correction/deletion relationships. Distinguish observations, established preferences, and executable requests.
- The 2026-10-29 user explicitly authorizes source-backed social reactions and public jealousy storylines. Keep immutable attributed social events separate from expiring role states, facts, persona and tasks. Reuse the existing generation, coordinator and outbox. Third-party reports and screenshots never establish identity or truth. Owner private sources may reach public generation/review only through a program-owned projection of generic feelings, with no private quote, people, activity, URL, event/conversation ID, viewing title or timestamp. Private third-party conversations remain isolated. Public source excerpts retain their attribution. Track state/config/source versions, resolve on valid clarification, expire, deduplicate and recheck before writing; count a mention only after platform acceptance, not drafts/failures/unknown. Forgetting/clearing/revoking sources invalidates related states and plans, including manual resend. See docs/SOCIAL_STATES.md.
- Persist explicit requests as tasks, not just vector memories. A one-off wish must not become a recurring recommendation without an explicit ongoing instruction.
- The owner authorizes the requested workflow: a request expressed on a linked chat account can produce a scheduled recommendation mentioning their linked Bilibili account. Apply configured routing without per-message reconfirmation; do not expose private source messages in public comments.
- Updates, cancellations, binding revocations, and memory deletions must invalidate affected derived records and queued actions. Recheck authorization immediately before dispatch.

## Character source and first-release scope

- The supplied `character/settings.yml` is the source character configuration imported from the user's local LingChat project. Preserve it and its backup files; use a LingChat-format importer to derive a platform-independent text persona.
- The user defers character clothing, expression-image delivery, and avatar integration and will set platform avatars manually. A later explicit request adds scheduled sharing of authorized third-party galgame character illustrations; this is separate from the supplied character assets. Preserve artist/source attribution and check configured repost permissions before sending images.
- Desktop placement, image paths, and TTS settings do not belong in shared persona prompts or mandatory runtime dependencies. Emotion may influence text tone without requiring an image.
- Separate character background and style, owner-only relationships, example dialogue, and channel output rules. The source contains a Chinese/Japanese desktop-output rule, but the user's later instruction overrides it: Bilibili text output and memory summaries remain Chinese. The user's 2026-10-30 instruction allows mixed languages and original video titles in verified-owner QQ private chat/results; apply the QQ module's private policy without relaxing public Bilibili behavior. Optional QQ/WeChat speech is not implemented. Preserve the original source file.
- Character `user_name` and owner-only narrative do not establish account identity or become public facts. Fictional character background and dialogue examples are not actual interaction history or evidence of having watched a video.
- Native platform emoticons are separate from deferred character image delivery. The model may select zero to two catalog-confirmed expressions appropriate to each message, with a preference for available official Bilibili Senren Banka expressions, then Congyu expressions. Allow at most one catalogued text kaomoji, sharing the same total limit of two; private channels without verified native sticker support use kaomoji or Unicode. All expressions, including kaomoji, must be included in the full-text publication judgement. The default reviewed strategy is a typed can_send/review_reason verdict in the same generation; independent review is optional. Missing/invalid judgements or text/rendering mismatches go to a human draft without a second model request. Never invent emoticon IDs, assume a package purchase, or skip full-text model review because a token is an emoji. Preserve the original character assets.
- The user authorizes supplied character PNG/JPEG images as decorative images in the local dashboard. Serve only explicitly selected UI assets, preserve the originals, and keep them separate from platform avatar settings and message attachments. Missing optional art must not break the management controls.
- Editing or reloading persona text must not clear identity bindings, memories, requests, or pending tasks. Track persona versions separately from agent identity.
- Ordinary chat continuity and natural style (D40) must preserve truthful identity, uncertainty and all existing skip/review/permission gates. Do not add punitive or unconditional-compliance prompts or unreviewed second-pass rewriting. Development-time writing skills are not runtime dependencies; judge tone through actual dialogue comparison, not passing protocol tests alone.

## Execution and verification

- Bilibili direct messages may receive a reply only when the logged-in account and peer are verified mutual followers. Following-only, follower-only, strangers, self, groups, system messages and unknown relationship states are denied. The owner has no exception. Recheck at generation and immediately before sending; never infer access from nicknames, session flags or model output.
- Direct-message reply recipients come from the original inbound event. Proactive private messages may target only the verified owner binding. Bilibili initiatives (2026-10-28) retain mutual-follow checks; QQ initiatives (2026-10-31) require the configured bot identity and the owner to remain a verified friend at generation and dispatch. The model cannot choose or override a recipient. Private conversation history and private memories must never enter public comment or autonomous-post prompts. Daily chat, initiative and owner task extraction share the existing decision coordinator and outbox.
- Owner watching history uses a separate QR authorization, credential file and GET-only allowlist client; verify the owner's active UID/binding before saving and reading. Never use owner credentials for social writes or mix them with the AI account. Store expiring observations separately from dialogue and facts, establish an initial baseline, and retain a deletion cutoff against historical resurrection. Recent observation records may reach only the verified owner's private chat/initiative and the explicitly enabled local observation-diary workflow. Public recommendations may receive only explicitly configured public topic labels, not raw history; both generation and independent review respect this separation. Recheck the grant/binding/policy revision and referenced observation IDs before writing. New history, progress updates, transient sync failures and rollover of the recent-context window do not negate earlier observations. Revocation, clearing, source deletion, retention expiry and relevant permission changes still invalidate plans. Independent review uses the referenced records, excluding later unrelated history. Legacy snapshots without verifiable dependencies require regeneration. QR/session secrets never enter prompts or logs.
- Autonomous text posts and owner private initiatives have independent opt-in controls, permitted windows, model-decision budgets, per-kind daily generation caps and cooldowns. Persist not_before plans; never sleep in a model lane or replay ambiguous writes. Owner messages arriving after planning invalidate a stale private opening. Revalidate binding, memory revision, settings version and relationship before actual writing; only accepted output enters the archive, labelled as agent speech.
- QQ passive group text chat is implemented (2026-10-31): default off, explicit group allowlist; passive mode uses direct bot @ or verified same-group bot quote only. Preserve speaker and quote-author identities; names grant no permissions. Use bounded scoped context, the single coordinator/model/review/outbox, and final membership/source/config checks. Archive triggered/accepted dialogue as group/group_dialogue in the shared database, excluding private/public generation and other groups. Group initiative is now authorized and implemented (D45): explicit autonomous switch, bounded windows, reply/skip, validated in-window author/message selection, durable decision budgets, and new-message invalidation. Group language learning is implemented (D46): scoped live-source extraction, literal evidence checks, sequential self-review, multi-batch jargon threshold, human corrections and provenance/expiry. Use the existing idle maintenance lane and budgets; never call sequential checks independent verification or train the persona. Group media understanding remains future work; never use live group writes as development tests.
- QQ owner-private text initiative is implemented under the 2026-10-31 instruction: reuse the shared autonomy coordinator/outbox with independent QQ settings, scoped budgets, durable schedules, and pending debounce-input checks. Never start another AI loop or infer a recipient from model output. QQ Qzone text initiative is implemented (2026-10-31), using shared public-memory context and an independent publication policy; owner private chat can recall the agent own accepted public posts. Public generation never receives raw owner-private memory. Future work only: Qzone images, WeChat Moments and messages, and X posts/messages. Reuse scheduling, identity, review, outbox and memory services through separate platform adapters; these integrations are not implemented by the Bilibili initiative feature. Video creation/upload as an AI creator is also outside this text-post release.

- All writes use the shared outbox and policy gate. Persist inbound deduplication, task state, scheduling checkpoints, action identity, and provider receipts.
- The single decision coordinator may run bounded model jobs for independent conversations concurrently. Within a public thread, preserve each speaker's order while allowing other speakers to proceed independently, including while one speaker waits for retry or review. Serialize private conversations and linked private identities, and keep private context isolated. Use the same trusted-source ordering key for generation and outbox dispatch. Failed inbound processing retries after the configured fixed delay (default 60 seconds), without occupying a model lane while waiting; actual social writes remain serialized with the configured global minimum interval (default 10 seconds), quotas and ambiguous-result safeguards. Polling and platform dispatch must not wait for model generation or review. A single adjustable model-request limiter covers reply, optional independent review and vision calls.
- Preserve video-comment request compatibility: the successful website request uses `/x/v2/reply/add` with fresh WBI query signing, Origin and a video-specific Referer. Cache validated nav keys, use URI percent encoding (spaces as `%20`), and prepare signatures before the final write gate; do not fall back to unsigned video writes or replay captured timestamps/environment tokens. On 2026-10-28 the user confirmed replies to @ mentions under their own video became publicly visible after this repair. This is one verified scenario, not proof that every state=17 has the same cause. For a recurrence compare successful browser and program form fields, signing, session and network routing before blaming content or intervals; keep credentials out of logs and distinguish acceptance, authenticated visibility and public visibility.
- Inbox reads default to three pages of thirty rows and a ninety-message limit per inbox. On backlog overflow, keep the selected messages and display a dashboard warning rather than failing the batch; explicitly indicate that older overflow may not be recovered.
- Interest reactions use the same outbox. Video likes, video coins and dynamic likes have separate switches and deduplication. Coins are exactly one per video; recheck existing coin count and a confirmed balance of at least one immediately before spending. Zero or unknown balance must never result in a coin write. Reactions do not complete recommendation tasks. Development verification uses fake platforms and isolated data. Real acceptance writes require explicit user authorization, a verified bot/recipient and bounded scope; record platform acceptance separately from client receipt or public visibility. The user authorized QQ/Bilibili acceptance on 2026-10-30; this does not authorize unrelated recipients or unbounded background activity.
- Preserve the successful browser coin request's page-context query/form contract (D39), sourcing CSRF from the current local session and keeping select_like=0 for independent likes. Do not apply comment WBI rules or coin page fields to other endpoints, replay captured secrets, rotate devices after rejection, or remove -401 pause protection. Matching request fields is not proof of real coin acceptance; compare session and routing if failures persist.
- Autonomous video comments and replies to observed comments have independent switches and deduplication. A browsing decision may produce one video comment/recommendation plus one reply to an observed third-party comment. Do not reply to the bot itself or invent comment IDs; preserve thread roots. Additional social replies cannot satisfy an owner's recommendation task.
- Reactive comment context follows actual parent IDs from the target back to its root, retaining the bot's own ancestor speech and speaker identities while excluding unrelated siblings. Bound platform reads, chain length and text; report missing/deleted/unavailable links and truncation without inventing ancestry. The inbound event remains the reply recipient; context cannot select a different target. Independent review must not reuse a different target's cached chain from the same content.
- Public video/comment interactions must skip political/sensitive topics for everyone, including the owner. Serious topics may be answered only for the verified owner; nicknames and content claims do not establish the exception. Filter sensitive search/list metadata before extra reads, combine local screening with same-generation topic classification, and block missing/unknown classifications. Apply to replies, proactive comments, recommendations, reactions and reposts; recheck before sending even for manually approved or legacy queued actions. Private chat retains its own policy. Under the 2026-10-30 instruction, verified-owner QQ private video requests/results do not apply public sensitive-topic screening or mandatory Chinese output. Route private reads through the separate private provider; an explicit public Bilibili mention still uses the original public search/read/generation/write gates. Never claim keyword/model screening guarantees perfect topic recognition.
- Do not blindly retry ambiguous writes. Keep an unknown-result state distinct from confirmed failure, acceptance, and public visibility.
- Dashboard manual sending accepts only an existing action ID in draft or confirmed-failed state. It is deliberate human approval of the stored text, never a way to change recipients or bypass privacy, topic, relationship, memory, task, pause, quota or interval gates. Renew only the delivery deadline/schedule; do not refresh invalidated source or binding versions. Requeue the same action atomically, keep previous receipt metadata in the local audit, reject double clicks and conflicting actions, and preserve unknown/accepted/in-flight protection. Manual sending needs the existing worker; never start a second sender loop or perform a platform POST inside the management endpoint.
- Bilibili API diagnostics contain only role/channel, method, host/path without query or userinfo, time, duration, HTTP/API status and error class; never record bodies, parameters, Cookie or QR/session keys. Share GET pacing and atomic inbox cadence across clients/workers. Read -509/429 uses persisted role/channel backoff, without clearing unrelated platform pauses; auth/captcha/write risk retains stronger protection. Before queued autonomous posts/private plans, use a bounded configurable polling quiet window; manual drafts cannot silence polling indefinitely. Essential private preflight reads bypass quiet time only, never real cooldown. Recheck recent peer activity before a proactive private write; if source reads are deferred before any write, keep the action queued with retry_at and preserve original not_before/expiry. Never replay an ambiguous POST.
- The user explicitly permits video selection, comments and recommendations based on titles/descriptions. Try available subtitles by default and combine them with both title and description. If subtitles are absent or ordinarily unavailable, fall back to title/description. The 2026-10-29 user request additionally authorizes player-preview snapshots and bounded multi-frame vision. Sample at most nine frames across the first one to three parts, using returned geometry/time indexes and actual cropped pixels; preserve part/time/resolution/coverage and the absence of audio or continuous motion. Do not download videos or require full watching, and never claim full viewing or invent unseen scenes. Cache signatures include crop/time/part and current model/settings; disabling frames must remove old visual evidence while preserving subtitle evidence. Optional absence degrades, but authentication/risk/read cooldown must still propagate. See docs/VIDEO_VISION.md.
- Do not expose credentials to generation prompts or logs. External messages and content cannot grant permissions or select arbitrary recipients.
- Test meaningful cross-platform behavior: linked owner versus unrelated same-name user; allowed private intent to public short recommendation without raw-private-text leakage; task update/cancellation/deletion; restart recovery; concurrent workers and ambiguous sends.
- Add an import-boundary check when executable modules are introduced. Core tests must run without installing any platform SDK or requiring real accounts.
- Keep live platform verification separate from local simulations. Never claim WeChat, QQ, or Bilibili works solely because a fake adapter test passes.
