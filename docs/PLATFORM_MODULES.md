## 实际边界

```text
src/murasamebot/
  bootstrap/
    platforms/
      __init__.py     PlatformModule、惰性工厂注册、平台状态准备、资源释放
      bilibili.py     原B站构造参数、通知/私信/主人内容轮询、平台专属发送策略
    runtime.py        共享模型/角色/视觉/记忆/引擎装配、模块生命周期与最终策略
    config.py         平台启用校验、旧配置默认值及兼容入口
    workers.py        一套消息/审核/发送/后台/维护协调器
  adapters/platforms/
    bilibili*.py      保持原位置和导入路径，未迁移或修改协议实现
  application/engine.py
                      一套业务引擎，领取工作时接受当前平台/账号路由
  adapters/persistence/sqlite.py
                      原事务队列，按路由过滤领取与可运行统计
```

保留`Runtime.platform`作为主平台的兼容入口，类型不再绑定B站；新代码使用`Runtime.modules`或`require_platform(name)`明确平台。旧的`Runtime(config, store, platform, model, engine)`构造方式仍用于B站兼容。主内容平台有B站时仍选B站，否则选启用列表中的首个平台；这不代表已经实现任意平台间的内容任务投递。

为减少对B站AI的影响，Q0解耦自身不移动`adapters/platforms/bilibili*.py`，不改签名、评论、私信、字幕、预览帧或表情协议。无需修改数据库schema、迁移既有事件ID、重建记忆或重新扫码。工作区同期出现的B站设备凭证、视觉与JSON修复属于并发任务，保留并另做整合回归，不能视为Q0修改内容。

## 启用与禁用

默认模板新增：

```yaml
platforms:
  bilibili:
    enabled: true
```

旧配置缺少`platforms`时默认启用B站，既有`bilibili`、`browsing`等配置继续使用。`config.local.yml`可以覆盖开关；`platforms`目前只接受平台名与`enabled`布尔值，凭证不放在这里。禁用B站后，其客户端、主人观察、插画来源与轮询不初始化；仅启用假QQ模块的测试配置无需B站凭证或完整B站配置。

当前默认工厂只有B站。直接配置`qq.enabled: true`会明确报告“尚无连接器”，不会退回B站或启动假QQ。所有平台关闭时可构造离线Runtime并查看本地状态；持续工作循环仍要求模型以及至少一个已配置的平台。真实QQ登录/连接在Q1实现。

禁用平台的事件、待审和待发动作保留状态，领取时跳过；正常过期、遗忘、撤权和恢复规则继续生效。当前进程的发送路由和最终策略会重读启用开关；新增模块、连接参数与完整生命周期变更应重启进程。已经在途的HTTP写入不能靠配置修改保证撤回，结果不明仍是unknown。

## 新连接器如何接入

1. 在独立的平台适配器目录实现需要的既有端口，如`ActionSink`、`PrivateMessageAccess`或`ContentProvider`。不导入另一个平台的适配器。
2. 在`bootstrap/platforms/<name>.py`提供`build_module(config, store)`，返回`PlatformModule`或其子类；仅在工厂被启用调用后导入协议实现、创建客户端。
3. 在惰性工厂表注册模块。测试可通过`build(config, platform_factories={...})`注入假模块；不新增第二套模型、记忆、业务协调器或sender。
4. `capabilities`声明支持的动作kind，另外可声明`content`、`exploration`、`emoji`等能力。它是程序能力约束，不是模型输出；最终策略拒绝未声明动作。平台权限、账号和收件人还须由适配器复验。
5. 轮询模块实现`poll`/`poll_private`；推送模块通过`Runtime.ingest`进入统一持久化与去重。原始事件必须先有真实平台、账号、发送者、会话和事件标识。默认规范化把平台/账号加入事件与会话ID；B站沿用既有带命名空间的标识，保留历史来源和删除标记。
6. 平台特有控制放在`guard`、生命周期与能力实现中。`background`不得自行调用模型建立另一条角色回复循环；共用现有后台调度与outbox。平台客户端和额外资源交由统一关闭，重复引用只关闭一次。

当前协调器会为不同工作任务构造各自的Runtime/客户端。Q0提供推送事件的规范化入口，但尚无QQ长连接资源管理。Q1若采用WebSocket，必须为长期收件连接设置唯一I/O属主和重连流程；工厂不能在每个生成、审核、发送任务中自动启动新的订阅，避免重复收件及不断重连。收件连接与角色决策仍分离。

目前每个平台只支持一个模块及一个机器人账号，路由校验使用`(platform, account_id)`；不宣称已支持同平台多账号。账号已知时旧账号动作不会被领取，账号尚未知时仍由协议适配器登录及发送前校验保证身份。Q1新推送接入应在登录确认账号后接收事件。

## 保留的共享策略

- 一个业务协调器和一个outbox领取/发送入口，模型并发与额度共享；平台暂停与原有B站读取退避继续独立。
- 全局串行写入与默认10秒最小间隔不变；处理失败重试默认60秒，unknown不自动重发。
- 人工审核发送按动作实际平台/账号查注册路由；不受“只能发主平台”的旧限制，也不绕过原权限、记忆、任务和来源校验。
- B站私信互关规则、首次基线、主人绑定、防自循环及已有检查点保留；B站私信开关不应用于QQ动作。
- B站观察只在B站模块启用时装配。本轮未为QQ私聊新增直接观看列表输入；既有带来源角色线索仍按原授权用途过滤，观察日记不进入普通聊天。关闭B站后，本地心情与记忆页面可以使用，未授权的观察日记不展示。
- B站自主配置变化只取消B站待发主动计划，不取消其他平台计划。共用全局设置的其余版本检查继续保留。

## 尚未包含

本轮不交付真实QQ收发、群聊、语音、空间、分平台主动计划调度、同平台多账号或微服务。视频搜索来源与结果投递渠道的独立任务模型属于Q2；现有视频委托仍以主内容平台为目标，未启用内容能力时明确报告不可执行，不把QQ自动当成视频搜索源。

`Behaviour`的B站默认值、部分B站配置校验和管理台专属入口继续作为兼容层保留。B站轮询中的既有水位、请求通道与检查点未改名；没有为目录整齐而批量迁移数据。维护公平性、备份、Docker与B站实号长期验收仍是独立待办。
