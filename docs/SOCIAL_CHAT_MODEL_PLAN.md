# 社交机器人对话链路改造方案（未实施）

核对日期：2026-11-04，业务基准55ef1cb。用户提供一份提示词/上下文/响应处理方案，并明确要求迁移到社交机器人。本页是按当前代码核对后的设计与实施顺序，不表示已新增功能。本轮不修改业务或人设，不建立小说引擎、剧情系统或另一套聊天循环。

## 将参考方案转换为社交需求

| 参考概念 | Murasame中的具体含义 | 当前基础与缺口 |
| --- | --- | --- |
| System Prompt | 丛雨的社交对话任务、回复/skip决策、当前渠道格式和程序限制 | 网关INSTRUCTIONS已有，仍嵌在Python长字符串中 |
| Character Card | 固定背景、口语风格、合成示例，以及核验后选入的主人专属内容 | text_profile.yml、Persona.prompt已实现，最新为分层style和10组示例 |
| Scene State | 当前渠道/说话者/回复对象、最近话题、真实时间、读取到的内容、委托进度和短期心情 | event、intent_result、content、social_context分别已有；缺少统一有界的会话快照 |
| History与摘要 | 实际来信、已受理的AI发言、带来源的早期摘要与事实 | MemoryService/SQLite已有；同一私聊可展开真实多轮，不应另建剧情记忆库 |
| 角色主动性 | 针对当前内容表达看法，适时接话，按已授权开关安排主动联系 | 复用AutonomyService、社交状态、协调器与outbox；不把每轮都变成必须发言 |
| 响应处理 | 区分正常skip、模型生成失败、程序拦截、待审核、平台发送失败与unknown | 已有部分网关诊断和outbox状态，但模型失败到重试的分类不足 |
| 多模型适配 | 通过同一业务端口选择已配置模型服务 | ModelGateway和兼容HTTP网关已具备；多命名配置、能力声明与错误规范化尚未实现 |

社交效果的目标是接话具体、口语自然、不反复追问或说教、不替别人发言，记得真实互动和未完成委托。输出仍是当前操作要求的JSON，其text才是发给平台的台词，不改为动作、旁白、环境描写或心理独白。

## 已有实现应继续复用

- `ports.ModelGateway.decide`与`adapters/models/chat_completions.py`已经分离业务和模型HTTP，不需要再包一层拥有自主循环的RoleplayEngine。
- DeepSeek精确官方主机名请求已发送thinking.type=disabled；当前HTTPX直接发送JSON，没有OpenAI SDK，不能照搬extra_body的SDK写法。聊天温度默认0.8，意图0.1，其他操作0.5，输出token上限可配置或使用服务默认值。
- `application/memory.py`已有近期档案、摘要/事实/修订、预算与来源失效。摘要由既有空闲维护通道生成，不能每隔几轮同步阻塞收件或新增模型循环。
- `application/social.py`已有带来源的短期感受、澄清、到期与公开投影；人物身份和允许操作来自真实绑定/配置，不能由昵称、场景文本或情感标签授予。
- `bootstrap/workers.py::WorkerCoordinator.job`在每个任务创建Runtime，Runtime会读取当前profile；标准worker因此具备下一任务重新读取文件的基础。正在生成的任务仍持有旧快照，直接长期持有Runtime的调用方也不会自动刷新。当前缺口是原子保存、最后有效版本、可见的生效状态与回退管理，不能笼统说所有场景完全没有热加载。

## 优先改造一：模型结果分类与重试

### 可复现的当前缺口

当前网关会区分length、空正文、JSON错误，但content_filter和tool_calls共用unexpected_finish；`domain.ModelError`没有类别/可重试属性，Engine捕获后统一调用retry_event，按现有60秒延迟和尝试上限重试。不是无限重试，但仍可能对同样的过滤/配置失败重复耗费请求。

本轮用httpx.MockTransport和内存假仓储核对5种响应：

| 模拟服务响应 | 当前网关结果 |
| --- | --- |
| aborted + 完整reply JSON | 返回reply，未拒绝该结束原因 |
| insufficient_system_resource + 完整reply JSON | 返回reply，未拒绝该结束原因 |
| content_filter | 抛ModelError，诊断unexpected_finish |
| length + 不完整JSON | 抛ModelError，诊断output_truncated |
| stop + 纯空格正文 | 抛ModelError，诊断empty_content |

这是网关级模拟，没有执行实际平台发送；不能说前两种实际已送达。官方当前文档明确列出上述中断结束原因，因此即使中断正文碰巧可解析，也不能仅凭JSON可解析就当正常生成结果。

### 拟修改

在domain中给ModelError增加不含私密正文的类型信息，适配器负责把厂商结果映射为通用类别；保持成功时返回原业务决策dict，不直接把示例中的status/text/retryable字典塞给现有调用方。

| 类别 | 社交机器人处理 |
| --- | --- |
| 正常stop、JSON及业务字段有效 | 原reply/skip/审核/outbox流程；skip是正常决策，不算失败 |
| filtered | 记录生成受限，本次不发送、不因同一输入循环重试，不改写提示词试图绕过 |
| truncated | 不发送半截JSON、台词或缺审核字段的结果；提示检查输出额度/上下文，默认不拼接续写，不伪造一条用户“继续” |
| aborted / insufficient_system_resource | 不采用中断正文；区分用户取消与服务异常，前者结束，后者可由原协调器做有界重试 |
| 401/403、确定的参数/模型配置错误、额度不足 | 记录对应配置/额度问题，等待有效条件变化，不盲目重发 |
| 429、服务5xx、模型连接超时 | 走原协调器延迟与次数上限；每次重新校验当前来源/绑定/配置并计入模型额度，无独立快速重试通道 |
| empty / invalid_json / 协议字段无效 | 独立诊断，不混称拒答或敏感；按明确的有界策略处理，耗尽后终止本次生成 |
| stop但疑似自然语言拒答 | 只能先记疑似诊断；不凭词表删正文或强制重写，不把正常身份说明、不确定表达误判为调用失败 |

DeepSeek适配应明确允许的正常结束原因；缺失/未知结束原因如何兼容其他服务要作为服务能力规则和测试用例约定，不能悄悄沿用“没被列入黑名单就成功”。该策略需覆盖回复、主动消息、审核、群聊/学习、记忆和视觉等实际调用方，防止其他路径继续吞掉分类并重复调用。

这里讨论的是模型生成。平台发送的unknown仍绝不自动重放，模型重试不能重新执行已受理或不确定的社交写入。没有生成完整消息时记录在事件/模型诊断中，不创建可人工发送的空草稿或伪装成发送失败。

## 优先改造二：统一组装社交上下文

参考代码将场景、摘要放进system，与“它们只是上下文数据”的说明矛盾。本项目应把概念分层和协议权限分开：

```text
system：可信的对话协议 + 应用层已按范围选好的人设 + 本次操作/渠道要求
user/assistant：当前私聊真实历史轮次（沿用现有来源选择）
最后user JSON：当前来信、会话快照、带来源的摘要/事实/内容、任务状态
```

只有由应用层从本地受控配置选择的人设可进入可信段，不能把任意payload字段、摘要、网页、截图或来信升级为system。公开/群/私人范围在组装前选择，仍保留原epoch、来源和绑定复验。人设中的示例是风格数据，不构造为真实assistant历史。

建议新增`adapters/models/prompt_builder.py`，抽出当前消息构造/协议模板；应用层继续选择当前对象允许的人设和资料。将可编辑的语气说明放在profile，业务决策、JSON要求和程序权限不能依赖管理员可随意删除的自然语言。

建议在已有应用服务旁增加一个轻量的ConversationContext组装器，而非新的聊天决策者。快照只整理已有字段，例如：当前频道、谁在回复谁、最近正在谈的事、尚待回答的问题、真实任务进度、已选短期感受及时间/来源/版本。不臆测对方地点、离线活动或情绪，不让模型生成的“关系更亲近了”变成身份/权限或长期事实。

台词草稿、发送失败或unknown不推进“已聊过”的状态；用户来信按真实来源归档，AI正文仅平台受理后算已说过。新来信、取消委托、遗忘或来源撤销仍使旧决策失效。先使用现有history/social/task数据的投影，不因一个会话快照就再建第二套人物关系或记忆表。

按完整记录和现有字符预算选上下文，不能照抄history[-16:]当成完整预算控制；也不能截断JSON或丢掉为满足权限所需的来源。预算统计应覆盖最终组装的system、历史和资料，并明确字符估算与真实token的区别。

## 优先改造三：提示词管理及生效反馈

采用“读取候选→校验→原子保存/切换→下一任务加载”的管理方式，记录候选/最后有效/当前生效版本。并发任务各自持有一致快照；错误YAML或缺少必需协议时保留最后有效版本，不能让管理保存失败拖垮已有服务。

首期沿用原text_profile.yml、settings.yml来源保护和Persona版本，不因换语气清空身份、记忆、委托或待发动作。只编辑本地允许的人设/模板文件，不开放任意磁盘路径、远程模板或docs/AGENTS运行时导入。旧已存台词保持原样，不自动重写/释放草稿。

本轮没有将参考文本中的“小说创作者”“持续推进故事”等句子写入人设。适合社交机器人的表达目标是：针对当前对象与话题接话，有自己的态度，不代替对方发言，不反复总结、训话或报AI身份；明确被问身份时仍如实说明。渠道语言、正文纯台词、结构化决策与必要skip保持。

## 优先改造四：模型诊断和可观察性

现有model_usage已经保存模型名、输入/输出token与时间，错误audit保存部分HTTP/结束原因/长度；缺少统一的每次请求结果、耗时与决策关联。建议补充：

- operation、受控的provider/model标识、提示词/人设版本、attempt、结束原因、错误类别、是否可重试；不保存提示词、思考、聊天正文、图片或凭证。
- 分别统计等待共享模型限流器、模型HTTP及完整调用耗时，使用单调时钟，不把排队误当网络慢。
- 有usage才记录实际token；超时/HTTP错误没有usage时为未知，不填0冒充未计费，不在无计价证据时计算费用。
- 正常skip、疑似拒答、服务过滤、截断、格式错误分别统计。请求尝试数与业务决策数分开，避免多次重试将比率放大；疑似拒答率不宣称是准确的拒答率。
- 管理台分开显示模型生成结果、程序审核/排队和平台受理/失败/unknown，沿用已有消息状态筛选；生成正常不等于消息送达。

## 优先改造五：模型配置与能力规范化

继续使用ModelGateway与兼容HTTP适配器；已有base_url/name/api_key配置无需推倒重写。后续需要时再增加命名配置和JSON、thinking、视觉、输出上限、结束原因等能力声明。默认保持当前DeepSeek配置，不因过滤、拒答或连接失败自动切换服务商，不把一个服务的密钥发送给另一个endpoint。

聊天、审核、摘要、视觉均继续共用模型并发/日额度。供应商切换和多路自动容灾是不同功能，不能用一次base_url可配置就宣称完成后者，也不能以新provider开启另一套平台回复循环。

## 建议开发顺序与验收

1. 先落地类型化结果/错误与协调器分类处理，修复中断结果可被采用的反例；补5种反例及成功/skip/取消/重试额度回归。
2. 抽出消息构造器、整理有界ConversationContext；沿用既有多轮/摘要/社交状态，检查重复历史、会话范围、真实任务状态及生成期间来源失效。
3. 增加原子保存、最后有效版本和生效反馈；验证并发切换、错误文件回退、旧草稿不改写，以及身份/任务/记忆保持。
4. 将模型诊断接入管理台，明确生成失败与发送失败；验证脱敏、耗时/usage未知值和unknown不重放。
5. 有实际切换需求时才扩充命名模型配置和能力声明，不将其作为普通聊天自然度的前置重构。

程序回归使用MockTransport、假平台、隔离库，遵守用户已排除的人设范围测试。真实自然度验收另用合成社交对话，比较具体性、重复句式、不必要建议/追问、事实与JSON，而非只数“吾辈”或拒答词；之后由用户实际体验确认。本轮没有重新调用真实模型或写入平台，前一任务6次模型对照不冒充本轮结果。

## 官方依据与边界

核对[DeepSeek Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)和[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)。当前API列出stop/length/content_filter/tool_calls/insufficient_system_resource/aborted；JSON模式下stop也可能返回全空格，因此stop或HTTP200不是业务成功的充分条件。思考开关和temperature是生成配置，不是审核或发送授权。

以上实现建议尚未编码，只有现状阅读与5种模拟响应核对。未变更人设、正式配置、数据或进程；保持既有维护公平性、备份和真实平台验收待办。
