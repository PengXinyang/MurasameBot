# 管理台评论状态核查耗时调查

调查日期：2026-11-04。仓库基准提交`358ec61`，工作区另有并发未完成的业务改动，本次不纳入提交。证据包括现有管理台的有界只读测速、已存脱敏请求诊断，以及隔离数据库/假平台时钟复现；没有重启正式服务、调用模型或发布/重发评论。本次完成原因定位，未实施性能优化。

## 实际观测

| 测量 | 结果 | 边界 |
| --- | --- | --- |
| 对一个已有已受理评论执行一次管理台只读核查 | 约15.86秒，HTTP200，查到state0，检查1页 | 核查结果写入原回执；没有社交写入，登录视角不等于独立公开验收 |
| 同次核查窗口内的登录nav请求 | 约3.14秒 | 是传输阶段耗时，不含请求前的读取排队 |
| 同次核查窗口内的评论列表请求 | 约0.129秒 | 本次评论列表返回本身很快，不能外推所有请求 |
| 一次页面第一批6个本机GET并发 | 约0.797秒 | 含status、QQ/B站列表、记忆、审计、服务状态，仅测HTTP，不含浏览器渲染 |
| 随后的3个记忆GET并发 | 约0.327秒 | 模拟现有刷新顺序；页面在更新B站动作列表前会等待这一批 |
| 当前配置读取 | 约0.345秒 | 一次样本，不视为所有机器的固定耗时 |

读取本机数据库时只查询表计数与脱敏请求字段，没有导出聊天、账号、Cookie或原始响应。此次各表计数查询约0～3.2毫秒，不能据此证明所有SQL或并发锁等待都很快，但未发现这些计数查询是此次十几秒等待的主因。

最近200条已存请求中，评论列表样本为98毫秒；nav中位数约143.5毫秒，但存在一次约27.1秒的长尾。不能将全部延迟归因于本地等待，也不能因为大部分网络样本很快就排除连接/响应长尾。请求窗口存在后台并发，现有诊断无单次管理操作的关联ID，无法完整还原每一毫秒的归属。

## 确认的调用链

1. `dashboard.html:operate`等待`POST /api/publication/check`。
2. `bootstrap/web.py`先加载配置、准备仓储，再`build(config)`装配完整Runtime；这里只需要发布核查适配器，但目前也会构造模型/图片/其他平台等客户端。
3. `application/publication.py`验证既有已受理动作及回执，取得该动作的核查租约。
4. `bilibili_publication.py`每次先调用`account()`读取nav，核对当前登录账号，再按真实目标读取1～2页评论。不请求模型、不发送评论，也不受社交发送最小间隔控制。
5. 每个GET都经过共享`RequestMonitor.before`，与后台通知、私信、历史、内容读取共用同一`request_slot`。当前读取间隔3秒，单次允许等待读取槽位最多10秒；这里会同步等待。
6. 查询返回后，`operate`调用全局`refresh()`。第一批6个管理接口全部返回后，还要等待`refreshMemory()`的3个接口，随后才重画B站动作列表。按钮恢复也等待整个刷新结束。

管理HTTP服务使用`ThreadingHTTPServer`，不是所有管理请求排成一条HTTP队列。平台读取槽位的共享串行间隔、每次完整装配和页面刷新屏障仍会让一次点击耗时叠加。

## 排队复现与诊断盲区

隔离SQLite、合成账号/动作和立即返回的MockTransport，使用产品默认读取策略及模拟时钟得到：

| 请求前已有排队 | 评论页数 | 总GET数 | 仅限流等待 |
| --- | --- | --- | --- |
| 无 | 1 | 2 | 3秒 |
| 9秒 | 1 | 2 | 12秒（9+3） |
| 无 | 2 | 3 | 6秒（3+3） |
| 9秒 | 2 | 3 | 15秒（9+3+3） |

以上没有真实睡眠或网络延迟，证明即使平台立即响应，现有队列也能产生秒级等待。后台还会在两个GET之间竞争槽位，实际等待不固定等于这张表。

`MonitoredTransport.handle_request`先执行`monitor.before(request)`，之后才设置传输计时起点，因此`platform_requests.duration_ms`不包含读取排队，也不包含Runtime装配、管理接口总耗时和前端刷新。仅看“平台接口耗时很短”无法解释按钮耗时；退避/静默导致的暂缓与真正发出的请求也须分开判断。

## 后续可优化位置（尚未实施）

- 给管理操作记录脱敏的阶段耗时：配置/装配、读取排队、平台传输、回执保存、前端刷新。关联值只能是本机操作用的随机值，不携带评论/账号ID或正文。
- 评论状态属于只读检查，可评估复用已有按凭证与账号校验的短期`read_account()`身份缓存，减少重复nav；实际发送前的身份复验保持原样。
- 核查完成后先更新该行状态与按钮，其他面板独立刷新；避免所有按钮操作等待9个无关管理GET和记忆渲染。
- 核查管理接口只装配所需的只读适配器，避免构造完整Runtime。各管理页的数据按需刷新，单独评估配置解析/重复仓储初始化开销。

不通过缩短既定3秒读取间隔、绕过共享冷却、自动重发、把缺失结果当state0或跳过目标/作者核验来换取速度。若后续改为后台查询，须保持同动作防重入、明确处理中/暂缓状态及真实结果时间，不能用旧结果冒充新核查。
